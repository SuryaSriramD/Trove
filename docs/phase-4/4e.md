# Phase 4E — Deterministic local automation

Implementation: `internal/workspace/automation.go`, `automation_runner.go`, `frontend/src/automation/AutomationPanel.tsx`.

## Execution and persistence

Rules belong to an authorized page and carry a stable ID, integer version, enabled/paused state, allowed origins, event or calendar trigger, optional typed condition, and 1–32 local actions. Saving a rule validates bounds and increments its version. Local owner scope is required to save/change/run rules; a narrower external grant cannot plant a rule that later executes with the owner's broader scope.

All canonical actions execute through the existing registered command handlers inside an isolated `automation.run` Batch. Every affected entity requires the normal permission and expected-revision checks. The rule page is itself guarded, so changing a rule invalidates an old preview. The committed event and mutation history use the `automation` origin. The final transaction writes both effects and a unique `(rule_id, rule_version, occurrence_key)` success record. Concurrent attempts, lost responses, sleep and restart cannot repeat committed local effects. Failed attempts roll back every canonical effect; diagnostics persist separately and three failures pause the rule.

A fresh retry uses the same original occurrence key and recalculates revision guards. Successful occurrences are never downgraded or re-executed. A failed event remains retryable after the scanning cursor has advanced. Editing a rule creates a new rule version; old history is retained.

The host calls `Kernel.RunAutomationTick(ctx, ownerContext, now)` while Trove is running. There is no hidden background service. Each pass scans at most 1,000 rules and 200 events per rule. Unchanged/irrelevant events advance a durable cursor; originated events are matched against their committed revision references. Import, restore and automation origins are rejected as rule trigger origins. User events are eligible by default; reviewed AI events require explicit rule opt-in.

## Rule/action subset

- Triggers: changed entity type or canonical collection, daily or weekly local wall-clock recurrence.
- Conditions: record/property `eq`, `ne` or `is_empty`, evaluated from current canonical values with normal derived-value diagnostics. Conditions are not evaluated against a reconstructed past workspace snapshot.
- Actions: page create/update, record create/set/clear value, task status. External side effects, processes, arbitrary code and external messaging are not supported.
- Recurring templates: saved canonical actions can contain `$id:name` placeholders; each expands to a stable per-rule-version/per-occurrence UUID. `{{occurrence}}` expands to the intended occurrence instant. Multi-command record templates use the same placeholder name to reuse an identity.
- UI: save a disabled daily/event note rule, inspect a preview, enable/disable, pause/resume, view outcomes and diagnostics, and review/retry a failed occurrence. The service supports richer typed actions and weekly schedules; the initial form exposes daily notes and collection-triggered notes.

## Timezone and missed-run policy

Schedules persist IANA timezone, daily/weekly frequency, local hour/minute, next intended instant, missed policy and catch-up bound. Occurrence identity is `schedule:<intended-UTC-instant>`; event identity is `event:<event-id>`. Recurrence uses calendar days, not 24-hour durations. Nonexistent DST wall times are skipped. An ambiguous repeated wall time uses the earlier UTC occurrence and cannot execute a second time in the repeated hour.

An occurrence within one minute of the runtime clock is due. Older occurrences are missed. The default `skip` records a skipped interval starting at the first missed occurrence and jumps to the next future occurrence. `catch_up` executes the oldest missed occurrences up to the configured bound (1–20), then records a skipped remainder and advances. This bounds work after extended sleep. No claim is made about exactly-once remote side effects because this implementation has none.

## Verification

`TestAutomationAtomicDedupRestartAndOrigin` proves effects and dedup survive closing/reopening SQLite and that committed event origin is automation. `TestAutomationRollbackFailureRetryAndPause` proves failed multi-action batches leave no partial pages and pause repeated failures. `TestAutomationCalendarDSTAndMissedPolicies` verifies independent New York DST and Kolkata expected instants, default skip and bounded catch-up. `TestAutomationExcludedOriginsAndEventDedup` verifies event replay/cascade exclusion. `TestAutomationFailedEventCanRetryAfterCursorAdvance` verifies guarded retry after unlocking a destination database.

The shared desktop integration owns the host timer. Schedules are explicitly documented and displayed as running only while Trove is running. Native backups preserve rules, occurrence receipts and history. A single-page revision restore does not re-enable or rewind a rule or clear its deduplication receipts.
