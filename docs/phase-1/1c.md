# 1C — Core database engine and tasks

Implementation owner: `phase1c_databases`. The implementation uses the Phase 0 domain and service contracts. There is one SQLite commit path: workspace `Mutation`. No view or renderer owns copied rows.

## Delivered behavior

- `collection.create` creates the collection and its immutable title property atomically. `record.create` creates a distinct record and its unique page body in one batch. The title value is a page-ID projection; renaming uses `page.update`.
- `collection.addProperty`, `record.setValue`, and `record.clearValue` support typed values. Numbers remain decimal strings and compare with arbitrary precision. Dates validate actual calendar dates, explicit time offsets, IANA timezones, and range ordering. Select/status options are checked against the owning property. Files use scoped file IDs, with canonical reference and history retention delegated to 1D.
- All requested P0 properties have editors: title, text, number, select, multi-select, status, checkbox, date/range, URL, email, phone, and files. Imported people/groups, author labels, original timestamps, and place values retain their original structured representation. The UI displays readable labels and an expandable raw-value preview without making imported identity into a local account.
- The `queryRecords` service applies nested AND/OR filters and stable multi-property sorting to the canonical records. Decimal sorting avoids floating-point conversion. Pagination cursors bind to collection, saved view, and both revisions; stale cursors return `CONFLICT`. Trashed records are excluded from view queries.
- Table, list, board, and calendar are saved presentation views. Settings persist filters, sorting, grouping/subgrouping, visible properties, calendar date/weekday, board grouping, and view name/location. Board cards and calendar ranges reference canonical record IDs. Drag/drop and keyboard-accessible select/date controls invoke `record.setValue`. A calendar move preserves range duration.
- `view.save` renames or moves the same view; it cannot silently switch its canonical collection. Containers link collections without owning or copying rows.
- `tasks.ensure` creates one system Tasks collection through an ordinary guarded batch. Repeated initialization is a no-op. `task.create` creates a record/facet there or in an explicitly supplied collection. `task.promote` adds a facet to the existing record and requires explicit default/done/reopen mappings. Only the system collection automatically binds its default Due property; promotion does not guess which date property means due.
- `todo` blocks contain only `{taskRecordId}`. Multiple occurrences, Tasks, and database views resolve the same title and status. Deleting an occurrence leaves the task intact. A task's bound status and a record's projected title cannot be cleared.

## Transaction rules

Creation requires absent guards for allocated page, record, collection, property, and view IDs as appropriate. Record edits require current record, page, collection, and relevant property guards. A record body/title change also touches its collection revision, invalidating view-query cursors. Record/page revisions remain equal. View moves guard both owning pages and the view. All operations inherit the kernel's scope, actor, approval, idempotency, history, and committed-event policies. `frontend/src/database/service.ts` centralizes these requests for the editor, Tasks surface, and database UI.

Queries authorize the collection and each returned page. Reference insertion validates task visibility. SQLite foreign keys and service checks reject values or views referencing another collection's properties. Invalid commands roll back the entire batch.
