# Phase 1D — Files, history, and recovery

The production implementation is in `internal/workspace/files.go`, `history.go`, and `backup.go`. It runs inside the workspace kernel's transaction, scope, revision, idempotency, and committed-event boundary. The desktop adapter chooses paths; renderer requests receive opaque file selection and ingest handles.

## Assets

`RegisterSelection` opens only a regular file with `O_NOFOLLOW` and retains the descriptor until the selection is consumed or expires. `prepareFile` accepts the canonical typed request, copies at most 1 GiB with cancellation checks, detects the media type, computes SHA-256, reserves one workspace file identity for those bytes, and publishes an immutable asset at `files/<first-two-hash-characters>/<sha256>`. Pending handles are bound to the actor and scope grant, expire after 30 minutes, and cannot be used by another grant. Content copying and hashing occur outside content write transactions. Atomic rename supports workspace volumes without hard links.

`file.attach` commits the canonical file row and relationship with the page body revision. A batch can attach to a block created later in the same batch; the final validator checks its page. Existing identical bytes reuse the canonical file ID. The file must have an absent or current revision guard, and record bodies also require the record/collection aggregate guards. Reference projections include media and preserved raw-file blocks, file properties, page covers, and meeting recordings. Removing a cover or media block removes live scoped access through that occurrence. `ReadFile` resolves an authorized file ID, rejects managed-directory symlinks, and verifies the stored length and digest before exposing the descriptor. The native HTTP adapter can serve ranged media using that descriptor.

P0 keeps every committed canonical asset for the lifetime of workspace history. `CollectAssets` can remove only abandoned, uncommitted blobs older than 24 hours after excluding live ingests and backup pins. This intentionally conservative policy prevents history or recovery points from becoming unreadable. A future explicit retention/purge service must supply its own reviewed scope and reference proof before reclaiming committed files.

## Revisions, trash, and restoration

Every mutation captures the page before and after, including blocks, page metadata, the same record's typed property values, task facet, and attachment references. Public historical `readPage` responses remain the canonical `ReadPageResult`; internal restoration metadata never expands that DTO. Page deletion is a timestamped tombstone. `history.list` returns the latest 500 revisions; `history.trash` returns up to 1,000 trashed pages filtered by scope.

`history.previewRestore` returns an expiring preview containing the historical page, asset IDs, and the complete current revision guard set. It binds the exact stored snapshot, actor, grant, and current page/block/record/collection/property/file revisions. `history.restore` consumes it in the same atomic batch that creates fresh page and record revisions. Stable block IDs survive restoration; deleted blocks are restored above their tombstone revision rather than rewinding to revision one. A stale preview, changed property schema, missing asset, moved block, deleted parent, or incompatible task promotion fails atomically. Collection definitions and other pages are never silently reverted. Restoring a page before a task promotion is refused while live task occurrences depend on that facet.

`history.recoveryPoint` stores a named event cursor and the exact page revisions in one write transaction. It requires workspace owner scope and an idempotency key; retrying the same name/key returns the same point and reusing the key with different content fails.

## Backups

`CreateBackup(ctx, execution, destination)` is a trusted native Go API; the destination must not exist. `backupSnapshot` serializes writers while persisting the backup lease and asset pins, then uses SQLite `VACUUM INTO` to produce an engine-consistent snapshot including committed WAL data. Writers resume before asset copying. Every canonical file in that snapshot is copied, hashed, and recorded with the database checksum in the versioned `BackupManifest`. An `INCOMPLETE` marker remains until every file and the manifest have been flushed. Cancellation or corruption leaves an explicitly incomplete export; a later open marks abandoned active leases interrupted and releases their source pins.

`VerifyBackup` rejects incomplete exports, unsupported formats, unsafe/duplicate asset entries, checksum mismatches, missing assets, or a manifest that does not match its database. Copy a verified backup to a working directory before opening it for normal mutations; opening the archive itself changes its database and therefore invalidates its original manifest checksum. Completed backups own independent asset copies and no longer need source-workspace pins. Their manifests, rather than a live WAL file copy, are the recovery boundary.

The recovery metadata migration is idempotent and records `recoverySchemaVersion=1` in `kernel_meta`. It is initialized while the exclusive workspace owner is opening the kernel. No worker receives SQL or write access to the workspace directory.

## Verification

`internal/workspace/recovery_test.go` exercises actual SQLite and filesystem operations: hash deduplication and distinct relationships across restart; scoped reads; symlink/handle rejection; stale preview conflicts; trash restoration with assets; monotonically restored block revisions; task/record state restoration without identity duplication; cover and file-property references; durable recovery-point receipts; backups opened as a fresh workspace; cancellation/interruption; history/active-backup retention; corruption detection and partial-backup rejection. The coordinator records the final shared test and packaged integration results in the aggregate evidence.
