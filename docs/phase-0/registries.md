# Versioned registry contract v1

`contracts/registries.json` enumerates every block, property and view family in TRD §§23–24. `contracts/domain.schema.json` supplies each entry's value/config schema. `contracts/examples/domain-registry-values.json` supplies one schema-valid example of every registered representation. Adapter IDs are stable interfaces to implement, not claims that renderers already exist.

## Envelope and version rules

The workspace format, service contract and each per-type schema have independent versions. The initial workspace format is 1; contract version is `1.0.0`; every registered type starts at schema version 1. Persisted `Block` uses `{id,pageId,parentBlockId,sortKey,type,schemaVersion,data,revision}`. Property definitions own `{id,collectionId,name,type,schemaVersion,config,revision}`; a record value is `{propertyId,schemaVersion,value}` with its type resolved through that definition. A view has its collection ID, query, type, schemaVersion, config and revision. JSON Schema plus registry dispatch validates the concrete data/config. Model/tool writes use exactly the same definitions.

Serialized native representations use UTF-8 JSON, canonicalized with RFC 8785 when hashed. UUID/revision strings remain strings. Stored source bytes are retained independently when byte fidelity matters. Dates retain explicit time-zone/time flags; decimal property numbers are strings and must not be rounded through binary floating-point. Arrays are ordered unless the type explicitly defines set semantics; `multi_select` is an ordered unique option-ID set. Normalization never changes stored source text merely because a renderer upgraded.

Unknown fields/types and future versions are never guessed into an editable known type. Decode into `unsupported_external` with `Fallback`: original source type/version, original JSON or immutable raw file reference, readable text and an explicit reason. Raw HTML/scripts remain inert. Lossless native export preserves the complete original payload. Missing renderers display readable text and a preservation notice. A known but noneditable P1/P2 construct can remain typed if its schema is understood; otherwise the same fallback applies.

Schema version upgrades are deterministic, pure, explicit steps from exactly one old version to the next. They preserve IDs, retain original payload/raw references and provide diagnostics. The registry's `migration.fromVersions` is empty for v1 because no historical native version exists; this is not permission to invent v0 data. Future migration registration requires old/new fixtures, deterministic replay, failed-upgrade preservation and downgrade readability tests. A workspace upgrade previews required changes, keeps a recoverable pre-upgrade backup and applies the approved migration through the workspace owner; failure leaves canonical content usable. Renderer upgrades alone never migrate storage.

## Required adapter behavior

Each entry specifies a schema, serialization rules, migration policy, readable fallback, renderer ID, text extractor ID, import/export representation and AI representation. The same registry entry controls feature claims:

| Adapter contract | Required result |
| --- | --- |
| Schema | Validate the specific type/version; property config also validates option IDs and type-specific settings. Reject dangling/cross-collection references. |
| Renderer | Display canonical content without canonical rewrites; an unavailable renderer selects fallback. UI preferences such as collapsed state, selection and playback position are not content mutations. |
| Text extraction | Deterministic text ordered by canonical block/cell order. Rich-text marks do not erase text; code/LaTeX/Mermaid source is searchable text; media uses alt/name/caption. A todo reads the canonical task title. Raw executable payload is never executed or treated as instructions. |
| Import | Emit the registered envelope, stable identity mappings, source provenance and compatibility result. Unknown or partial information is explicitly preserved. External checkbox input is adapted to D001, never stored as an independent `checked` field. |
| Native export | Lossless envelope with IDs, schema versions, provenance, raw references, links and a manifest of managed asset hashes. Native re-import can recover opaque data even with no renderer. |
| Portable export | Readable Markdown/CSV or supported HTML plus a raw JSON/assets sidecar whenever the portable format cannot represent structure. The export report identifies adapted/lossy presentation; it never claims the readable format alone is lossless. |
| AI read | Typed data plus `Location` and plain readable text within service budgets. Source material is untrusted. Resolve task/status and page-title projections live. Do not include executable/import-only raw payload unless explicitly requested as inert evidence. |
| AI write | A plan conforming to the same native type/version; only types with `ai.writable:true` at the enabled release qualify. Apply through review/scope/revision/idempotency checks, never through a renderer or direct SQL. |

For example, a paragraph extracts `richText[].text` in order; an unsupported tab extracts only its readable fallback while retaining original raw tabs/child IDs; a todo exports its task-record link and readable task title/status without creating a task copy. Plain Markdown may print `- [x] title`, but the sidecar carries `taskRecordId` and record/page identity needed for lossless round-trip. A title property's value is a `pageId` projection; a record never stores a duplicate editable title property value. UI and AI title edits issue `page.update` for the record body page with the page/record revision guards. Direct `record.setValue` for type `title` is rejected. Its registry `ai.writable` is therefore false for direct property-value writes; editing the canonical page title remains supported.

Block children are canonical Block rows. Layout schemas reference child IDs and retain source structure when editing is unavailable. Table cells carry IDs, positions, spans and pre-merge content. Semantic validation rejects overlap, gaps, out-of-bounds spans and width/header mismatches. P0 preserves supplied merged-cell spans and H4/tab data; native H4, tabs and merge/unmerge editing qualify at P1. View queries contain a typed filter AST, sorts, group/subgroup property IDs and visible properties; view layouts cannot contain a records array. Board/calendar drag operations become record property commands, not independent view state.

P0 editable block, property and view types are marked individually. P1/P2 registry entries establish representations and preservation behavior, not prematurely completed features. Imported identity/author/place values are preserved at P0; editing controls are P1. Formula/rollup/button and chart/form representations retain unsupported source in a typed fallback until their release work defines executable semantics, evaluators and associated migrations. No import is allowed to silently execute a formula/button or flatten its raw source into an editable string.

## Integration and verification

`reference_domain.validate_registry_value(family,type,schemaVersion,data)` is the conformance dispatch. `config=True` validates property definitions. `validate_snapshot` additionally checks graph invariants, registry references and current locations; SQL adds concrete relational constraints. `extracted_text` and `preserve_unknown` define representative extraction/preservation behavior. Production Go/TypeScript adapters must port these semantics and add per-type editor/import/export tests as features are implemented.

The contract checks cover every listed schema/example, raw unknown/future round trips, representative task text extraction, preservation of table pre-merge content and rejection of overlapping spans. Passing them establishes the Phase 0 interface gate. It does not establish implemented editor support, complete import fidelity or product verification; each feature still needs persistence, editing, search, import/export, AI and acceptance evidence linked in the ledger.
