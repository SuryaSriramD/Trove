# Phase 0 resolved decisions

Status: accepted contracts, version 1. These decisions supersede the ambiguous task row sketch and inline checked field in TRD §§5, 23. Changes require a contract version, migration/fallback story, updated fixtures and ledger evidence.

## D001 — Tasks are a record facet; todo blocks are references

A task has exactly one canonical record, unique page body, title and completion state. New standalone tasks are created atomically in the workspace's one system Tasks collection. That collection has a primary title property and status property with explicit done/reopen option mappings. `TaskFacet` contains `recordId`, `statusPropertyId` and optional `duePropertyId`.

An existing collection record is promoted by adding the facet to that record in place. The service validates a status property in its own collection, or explicitly adds one in the same approved schema mutation. Promotion never copies the record to Tasks and never changes its record/page IDs. The Tasks screen queries task facets across collections. A presentation view still references one collection; an all-tasks service result is a query projection, not a synthetic collection containing duplicated rows.

A `todo` block stores only `{taskRecordId}`. The displayed text derives from the task page title; done derives from its mapped status option's `group == "done"`. Editing either UI changes that one canonical value. A toggle chooses the collection's explicit `doneOptionId` or `reopenOptionId` under the expected record/page revision. Reopening does not infer a historical state. Multiple todo occurrences, Tasks screens, boards and database tables all project the same state. Nested todo blocks represent nested display structure; record parent-child task semantics are a separate future relation and are never inferred from every occurrence's indentation.

An imported standalone checkbox creates one record/facet and a reference block, preserving its original rich text and original checkbox state in source provenance if conversion loses marks. Re-import uses the mapped upstream block/record identity to find that task; a duplicate occurrence must not produce another record. Importing a checkbox already linked to a known source task uses that record. Matching by text alone is ambiguous and needs review. Local source-block display labels do not become alternate editable task titles.

Deleting an occurrence leaves the task alive. Trashing the record keeps readable unresolved occurrences until restored or explicitly removed. Detaching a facet with live todo references requires a reviewed conversion/removal plan. A memory note may mention a task but never stores a competing live status.

Executable evidence: task projection tests and SQLite `task_state` / `todo_references`; the example has two occurrences of one system task and one promoted record from another collection.

## D002 — Re-import is a three-way merge with preserved common baseline

For each mapped object, persist its last accepted source snapshot, raw source hash/file, source revision and local mapping. Normalize the new capture into canonical fields before comparing `base`, `local`, and `incoming`. Compare schema-defined atomic paths: title; each property ID; each block's payload, parent and order; individual attachment relationships. Rich-text spans and list reorderings are atomic until a versioned merge algorithm explicitly supports finer structure. Missing is distinct from JSON null; serialized field values use `{present:false}` or `{present:true,value:...}`.

| Comparison | Outcome | Write |
| --- | --- | --- |
| Local and incoming both equal base | `unchanged` | None |
| Local equals base, incoming differs | `apply_incoming` | Apply incoming field |
| Incoming equals base, local differs | `keep_local` | Preserve local field |
| Local and incoming match, both changed | `converged` | Preserve matching value |
| Local and incoming differ from each other and base | `conflict` | Preserve local value; retain incoming; review |

The plan identifies the mapping, exact local revision and incoming source revision. `ImportResolution` binds its own ID, the per-object `planId`, mapping ID, expected local revision and incoming source revision. Each field choice is `keep_local`, `take_incoming` or `merged`; only `merged` carries an explicit `FieldPresence` value. Every conflict path must be resolved exactly once. Ambiguous/missing identity requires `link_existing` or `create_new` with local kind/UUID, or `skip` with no content writes. Deletions require `keep_local`, `accept_source_delete` (only with proven complete source deletion), or `restore_source` (only for a local tombstone with live incoming content). Matched mappings cannot be silently remapped through a content resolution. Apply includes these typed resolutions inline, and history retains them. Applying it rechecks revision, scope and approval in the same atomic service batch. A stale plan is rejected and recomputed. Independent non-conflicting fields may be previewed separately, but an object with unresolved conflicts is not committed by default. An explicit review can apply selected fields and persist unresolved conflict records. A resolved object advances its common source baseline to incoming while keeping local overrides as local differences; a partially unresolved object retains the prior baseline and the full pending incoming snapshot until all conflicts resolve. Retrying an accepted import-run/item operation uses the same idempotency key and must return its prior result.

Deletion is an explicit case. Missing objects in partial or unknown-completeness captures are not evidence of deletion. A complete, authorized enumeration can propose tombstoning an unchanged local object deleted upstream. Locally edited content becomes a deletion conflict. A locally deleted object is not silently resurrected: unchanged incoming stays deleted; changed incoming creates a review item. Upstream moves retain IDs when source identity is stable. Ambiguous/changed derived locators or multiple candidates require manual mapping or explicit create-new; filenames, identical titles and file hashes cannot resolve page identity on their own. Collection/source boundaries remain distinct even inside one container.

A changed attachment produces a new immutable file and changes the relationship through the merge; identical bytes reuse the existing file. Old bytes remain retained when needed for local edits, history or the common baseline. The reconciliation report separately counts preserved, adapted, partial, unsupported-but-retained and failed discovered items. Source-absent information and unknown completeness remain separate claims. Permission or read failure never becomes an empty/deleted source.

Executable evidence: `domain-reimport.json`, `domain-reimport-plan.json`, `merge_fields`, `reimport_action` and their tests cover changed source/local content, independent fields, convergence, null-versus-missing, conflicting deletes, omitted source content and ambiguous identity. Production persistence/review UI remains in the importer work package.

## D003 — Project memory scope is explicit and closed by default

A project is a stable container with `kind:"project"`, an owning page and optional parent project. Its `ProjectScope` contains explicit member page IDs, pinned page IDs, exclusions and two opt-in preference inheritance flags. Effective pages are the live owning page plus explicit members/pins, minus exclusions. Page-tree descendants, backlinks, database relations, shared view placement and ancestor project pages do not implicitly join the scope. Creating/moving a page into a project through project services updates membership in the same mutation. A navigation-only move does not silently change retrieval rights.

Membership can be shared explicitly. Pinning a page from another project is an explicit cross-project inclusion visible in the scope preview. Exclusion wins over membership, pinning and inherited evidence. Scope resolution happens at retrieval time against the current membership revision and the current mutation/read grant; a saved query never widens a grant. Ancestor cycles are rejected.

Memory has exactly one of authored `content` or `pageRef`: `project_context` requires a page reference, while preferences and decisions require authored content. A context entry has no competing cached body string. Its normal memory page and source locators remain explicit. Only active, explicitly approved memory can enter retrieval. Project-local entries qualify for that exact project. Ancestor-project preferences qualify only if `inheritAncestorPreferences` is enabled; workspace preferences qualify only if `inheritWorkspacePreferences` is enabled. Both flags default false. Project context and decision history never inherit implicitly. A pages-scoped entry requires all its scoped pages to be in the effective scope. Cross-workspace entries never qualify. Inherited preferences still require their own source pages to be included; inheritance does not grant content access.

Every sourced entry is checked against live source page revisions and stable block/transcript locations before use. Changed, trashed or missing sources make it ineligible immediately and the workspace mutation marks it stale with revision/history/committed events. The read guard protects against delayed invalidation/index jobs. Project-context pins retrieve current original content; they do not blindly reuse a cached summary. Reapproval requires review of the new evidence. The memory's own page being trashed also disables it. Project deletion disables its retrieval scope; it does not erase explicitly shared pages or silently reassign its memories to a parent/global scope.

Explicit Forget disables retrieval in the committing transaction, writes a memory history event, and queues removal from live text/vector indexes. The read path always filters forgotten IDs even while index cleanup is pending. Backup/history retention and old conversation transcripts are separate controls, and forgetting does not claim secure erasure of those copies. Superseding a decision records the predecessor and makes it ineligible; newer live records remain authoritative. Conflicting applicable preferences are returned as conflicts for review rather than silently selected as facts. If explicit precedence is needed, project-local preferences outrank ancestor preferences, nearest ancestor outranks farther ancestors, and workspace preferences are lowest; contradictory evidence is still surfaced.

Executable evidence: project-page and memory eligibility tests cover approval, disabled/stale/superseded/forgotten states, source changes/deletion, exclusion, explicit inheritance, preference-only inheritance, and unrelated project rejection. Model-quality evaluation with/without memory remains the product acceptance gate.
