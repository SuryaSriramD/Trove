# Workspace service contract v1

`contracts/service.schema.json` is the wire authority. `contracts/service.go` defines the shell-independent Go service interface; `types_generated.go` and `generated/*.ts` are generated from the schemas. The Wails 2 facade delegates to this interface. All application content writes, import commits, job results, AI tools and eventual MCP adapters cross this boundary. No renderer, importer or worker receives SQL, an unrestricted filesystem path, a database connection or a writable workspace directory.

## Requests and responses

Persisted canonical fields follow domain naming. Staged file results use contentHash/mediaType/string sizeBytes and the canonical fileId; native pipe handle sizes remain bounded JSON integers and are converted without loss. Requests carry `contractVersion: 1`, UUIDv7 `requestId` and `workspaceId`. Every read and mutation validates the contract and session scope. Unknown fields, unsupported major versions and malformed registry payloads are rejected. Reads return a consistent snapshot cursor; paginated cursors bind collection/view, query hash and snapshot revision. Expired cursors require restarting the query. `QueryRecords` returns canonical record IDs and bodies, never view-owned copies. Scope is intersected with the server-issued grant before queries; search filters are not authorization.

CreateContainer requires database/project containerKind and a nullable parentProjectId; project.setScope updates the explicit scope under the container revision. AllocateIds reserves kernel-generated UUIDv7 IDs for pending create commands (abandoned IDs are never recycled); it grants no write authority. Methods include typed import preview/report and memory listing in addition to `Batch`, `ReadPage`, `QueryRecords`, `Search`, `ResolveCitation`, `ReadEvents`, `Cancel`, `PrepareFile`, `EnqueueJob`, `GetJob` and `CancelJob`. Typed requests and responses are named definitions. `Batch.commands` is the discriminated `Command` union. The frontend can construct concrete commands from generated types. Go calls `DecodeBatch` and validates other DTOs with `Validate` before dispatch. JSON Schema validation does not replace the semantic checks below. Wails transport exceptions become `INTERNAL` or `WORKSPACE_LOCKED` responses with the request ID; logs contain the correlation ID and redacted diagnostics, never full private content by default.

Responses use `{ok:true,result:...}` or `{ok:false,error:{code,message,retryable,requestId,details?}}`. Stable error codes are schema enums; clients branch on code, not message. `CONFLICT` includes current revisions, `APPROVAL_REQUIRED` includes the proposal hash, resource/busy failures may include `retryAfterMs`. Validation, scope, unsupported schema and approval errors are not automatically retried. Retryable worker/I/O failures use a bounded job retry policy. P1 tools are registered as unavailable capabilities until their product implementation and release gates pass.

## Atomic mutation boundary

The writer owns one serialized SQLite write connection (WAL, foreign keys, 5 second busy timeout); bounded readers use the same pragmas. One process owns the workspace lock. A batch is at most 256 commands and 4 MiB UTF-8 JSON. The queue holds at most 128 waiting batches; overflow returns `RESOURCE_EXHAUSTED`, not an unbounded renderer promise. No model, file copy, extraction or network work occurs while a content transaction holds the writer.

1. The adapter authenticates the local installation/client and constructs `ExecutionContext`. The renderer supplies only a scope grant and optional approval reference, never a trusted actor/origin. Validate shape, limits, registry versions and capability availability.
2. Resolve entity targets and every related write target (parents, both collections on a move, page body for record title/content, dependents invalidated by a change). Authorize the whole set against the current scope and policy revision.
3. Begin `IMMEDIATE`. Check `(workspaceId,actorId,idempotencyKey)` receipt. A matching request hash returns its recorded commit result, even after a lost acknowledgement; a different hash returns `IDEMPOTENCY_CONFLICT`. Replayed content is still subject to current read access. No content is written a second time.
4. Revalidate the grant, approval and all expected revisions inside the transaction. Kernel-derived memory/index invalidation is a registered system side effect: it may mark hidden dependent memories stale without exposing their contents or widening caller grants. The kernel guards those dependencies internally; clients guard only explicit content targets. Such invalidation is recorded with original causation and cannot edit or activate hidden memory content. Every affected existing canonical entity needs its observed revision; a creation uses `"0"` meaning absent. Missing or duplicate guards are `INVALID_REQUEST`. Revision guards are a set, sorted when hashing. Reject any unguarded discovered dependency and return the required revision set for a fresh proposal. Pages bump on every body change; record and body-page revisions form one aggregate and remain equal: property/title/body changes bump both; blocks have independent revisions. A touched entity increments once per transaction, even with multiple commands. Reject int64 overflow.
5. Apply all commands, domain constraints, history snapshots, idempotency receipt, durable committed event and derived job enqueue records in that same transaction. On any failure roll back all of them. Derived indexes never become canonical content. File bytes are already staged and hash verified; atomic rename completes before the file metadata commit. Unreferenced staged bytes are safe to collect after retention.
6. Commit, then publish events/return results. A disconnect after commit is an unknown acknowledgement, resolved by the same idempotency key. No success or committed event is emitted before commit. No separate listener is relied upon to persist history or invalidate retrieval eligibility.

Command hashes use RFC 8785 canonical JSON of workspace ID, commands and mutation metadata (including approvals and guards) and exclude request ID and cancellation ID. Approvals bind a proposal hash excluding the approval ID itself to avoid a self-reference. Approval storage records the latter; receipts store the former. Retain receipts for workspace lifetime unless an explicit export/retention process also retires the caller retry namespace. A key is never silently reused. Bulk imports use bounded atomic staging batches with durable checkpoints; the entire export is not one transaction. The report tells users exactly which batches committed before cancellation.

## Mutation policy and history

`ExecutionContext.actor` is the local execution principal; imported author snapshots are provenance only. Origin is one of `user`, `ai`, `external`, `import`, `restore`, `automation`, `system`, `migration`. A trusted UI intent maps to `user`; a model proposal stays `ai` even if accepted by the user. Approval does not relabel its origin. Import and restore cannot masquerade as fresh user edits. `causationId` and `runId` connect follow-up jobs and rules to their initiating event. P1 automation defaults to user/page-button events; import, restore, system, automation and AI are excluded unless explicitly enabled. Deduplicate a rule occurrence before executing local effects.

| Caller | Reads | Writes |
| --- | --- | --- |
| Direct user UI | Current workspace/granted selection | Explicit UI action authorizes its exact operation; destructive actions show the affected scope |
| Local AI | Selected scope and eligible memory | Exact reviewed proposal or bounded previously approved grant; all revisions rechecked |
| External client | Explicitly granted scope | Ask by default; delete denied by default; raw files require a separate grant |
| Importer | Selected source handles | User-approved import plan and mapped destination scope; conflicts require resolution |
| Jobs | Minimal approved inputs | Registered service operation tied to durable job and live lease; no arbitrary mutations |
| Automation | Explicit rule scope | Versioned approved rule and allowed origins; P1 capability |
| Migration | Exclusive workspace migration mode | Versioned migration after recoverable snapshot; not an AI capability |

An approval binds actor, workspace, scope grant, policy revision, command hash, expected revisions, expiry and approving user. It is single-use for a mutation, with replay through the receipt. Changed scope, changed proposal, expired/revoked approval or revised source invalidates it. Scoped approvals, when implemented, enumerate operation kinds, target roots and limits; they never imply delete, raw-file access or cross-project access. Memory approval always requires an explicit user action. Proposal drafts are not approved memory.

`mutation_history` stores actor/origin/causation, revisions, before/after snapshot references, approval, hash and committed time. Every restore creates a new revision and history item; it never rewinds revision counters. Deletion is a tombstone transaction with explicit descendant scope. Purge and retention are separate user operations. Diagnostic logs do not substitute for canonical history.

## Semantic checks per operation

- `page.create` creates an empty body. Root parent is null. `page.update` must contain at least one change; title is canonical for record title properties too. Moving cannot introduce cycles or cross-workspace parents.
- Block insert resolves `afterBlockId` within the same page/parent; absence means append. Services assign and rebalance fixed-width sort keys atomically. Reorder lists the entire sibling set without duplicates. `schemaVersion` and `data` validate through the registry; fallback blocks remain inert. Delete with children requires `includeDescendants` or fails. Block operations guard both block and owning page.
- Collection creation accepts titlePropertyId and creates that immutable title property in the same transaction; include its absent revision guard. Workspace bootstrap creates the one system Tasks collection and configured status options before task creation is offered. `record.create` always creates the given empty page body atomically. `record.setValue` carries ValueInput {type,schemaVersion,value} and validates the property's type/version/config; title is rejected here because it is a read projection; edit a record title through page.update with the record and body-page aggregate revision guards. Task create uses the workspace Tasks collection unless both collection and status property are supplied. Promotion adds a facet to the same record. Status options must belong to the bound status property.
- View save supplies `name`, `query`, registry type/config and existing canonical collection. It cannot contain records. Container links do not clone data. P0 can preserve P1 view definitions as inert fallbacks.
- Native file picker returns a session-bound `selectionHandle`; `PrepareFile` hashes/copies safe bytes and returns an expiring ingest handle. Attach validates hash, MIME/size and handle ownership. Arbitrary renderer paths and URLs are not allowed. The workspace has one canonical file ID per SHA-256. PrepareFile returns that existing ID on a byte match; AttachFile must use the returned ID. Attachment labels, relationships and source provenance remain distinct. Identical file bytes never merge page/record identities.
- Meeting segments require `endMs >= startMs >= 0`, unique segment/block IDs and consistent meeting/page/file. Retried segments cannot duplicate or overwrite different text under the same ID. Finalization uses captured duration and validates segment bounds. Corrected transcripts create new source revisions.
- Memory propose creates its pageId body and proposed entry atomically, guarded as absent; content is projected into that body by the memory service. It requires exactly one of content/pageRef; project_context needs a page ref, decision needs evidence and preference can be explicitly user-authored. Approval checks source revisions and project scope. Forget excludes retrieval inside the same transaction and queues active-index removal.
- Import adapters normalize staged objects into the domain snapshot/registry envelopes and ImportMapping identities before preview; unresolved source references become explicit fallbacks and report items. Staging receives IDs from AllocateIds and has no canonical write authority. Incoming source snapshots never import active approval or execution principals. PreviewImportResult.planId identifies the staged batch and its hash binds the complete manifest; each reimportPlans entry has a separate per-object id. Inline ImportResolution.planId binds that per-object plan, while ApplyImportPlan.planId references the staged batch. Apply import plan requires a current immutable plan hash, inline domain.ImportResolution objects for all conflicts, mapping/base revisions and all local entity revision guards. Restore requires a preview of affected entities/assets, current guards and a fresh transaction.

## Committed events and cancellation

`CommittedChangeEvent` carries event/transaction/workspace IDs, a decimal cursor, actor/origin/scope context, before/after revisions, tombstones and history ID. Outbox records commit atomically with mutations. Delivery is at least once; consumers deduplicate by event ID and checkpoint the cursor. Progress can coalesce; committed events and final job results cannot be dropped. `ReadEvents(afterCursor)` catches up after disconnect. If history retention has removed that cursor, return `requiresSnapshot: true`; the client refreshes a snapshot before resubscribing. Snapshot and cursor are read in one transaction.

Cancellation IDs are scoped to caller and workspace. Every Go method accepts `context.Context`; long work runs as a job. Before the commit boundary cancellation rolls back and returns `CANCELLED`. Once committed, cancellation returns `already_committed` with the transaction ID; it never falsely reports rollback. Concurrent cancellation and commit are linearized by the writer. Cancellation of a multi-batch import stops future batches and leaves a reconciled partial report. Job cancellation semantics are in `jobs.md`.

## Retrieval and citations

`domain.Location` is the only locator used by search, exported AI context, memory sources and transcript citations. `pageId` and exact `sourceRevision` are mandatory; block-derived results also require stable `blockId`, and transcripts require `meetingId`, `segmentId`, half-open `[startMs,endMs)` and transcript block ID. Page-only citations refer to the whole page at that revision. A file-extraction result cites the owning page and attachment block at its page revision; chunk metadata additionally retains file hash and extractor version. Offset-only or list-index-only citations are forbidden.

The source revision is the owning page revision of the cited snapshot, not the index version, import run, model version or current arbitrary page head. Block moves retain block IDs but old locations remain historical. Chunk IDs are derived from locator + source/content hash + extractor version; embeddings also bind model hash, dimension and index generation. Before presenting a factual answer, resolve every selected locator against current scope, tombstones and revisions. Deleted, stale, out-of-scope or unavailable sources cannot silently support a fresh claim; regenerate context or report uncertainty. Historical answers can show retained historical snapshots explicitly. P0 opens the page and highlights a block or seeks audio; the P1 full block-link UI adds presentation without changing locator identity.
