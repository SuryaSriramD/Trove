# Portable PDF parsing and export — implementation, qualification still open

The Windows source path uses an isolated native WebView and the already pinned PDF.js 6.3.289 resources. The Ubuntu helper source is retained, but Linux PDF text extraction and PDF export are now explicitly unavailable until enforceable ownership of the full browser process domain is implemented. The PDF viewer and HTML export remain available on Linux. The Windows helper preserves original input bytes, extracts the PDF text layer with physical-page separators, and renders the same canonical rich print snapshot used on macOS. On Windows, native-selected export destinations receive a new PDF only after bounded rendering, PDF.js page-count validation, and a final owner-grant check. No screenshots are acquired by this package.

The macOS PDFKit extractor and WebKit renderer remain the macOS implementation. The ambient `pdftotext` PATH fallback has been removed: missing installed helpers produce an explicit unavailable result while preserving the original. PDF viewing already uses the bundled PDF.js frontend on all desktop targets. DOCX/text/CSV/HTML extraction remains the existing portable Go implementation.

## Native boundary

`document-worker render|extract <private document directory>` consumes a one-byte start gate only after the parent assigns containment. Go verifies the target binary, production manifest, runtime pin, and every staged asset. It copies the executable and selected resource bytes into a new private directory. Windows creates these directories with an owner-only protected DACL. The disabled Linux source also defines a pinned WebKit web-process policy extension; production Linux execution never reaches staging. The helper receives no workspace database, application bridge, credentials, ambient proxy settings, or arbitrary renderer-selected paths.

The inventory accepts only the selected mode's fixed HTML entry, local bundled assets, a canonical snapshot and referenced managed images, or one retained PDF. Both native helpers recheck identities when serving content. Strict CSP, exact request paths, GET-only requests, no arbitrary navigation/popups/downloads/permissions, and no PDF JavaScript/action execution preserve the offline boundary. Invalid/present helpers never silently downgrade to an unrelated installed parser.

Windows uses the official hash-pinned WebView2 SDK 1.0.3537.50, installed stable WebView2 >=141.0.3537.50, an InPrivate profile, all-request-source filtering and native PrintToPdf. This minimum is separate from Wails' lower shell minimum. The helper refuses missing capabilities and runtime/profile overrides. It never downloads a runtime. See [Windows source review and SDK evidence](windows-document-helper.md).

The disabled Ubuntu source targets WebKitGTK 4.1 API with exactly 2.52.6 runtime and 2.52.6-0ubuntu0.24.04.1 development/runtime packages. An ephemeral context must acknowledge the loaded web-process policy before any document page is opened. Request cancellation runs on `WebKitWebPage::send-request` in that extension; response CSP independently limits resource loading. Print output explicitly selects GTK's virtual Print to File backend, never an ambient default physical printer. The exact Linux custom URI scheme can cause PDF.js to use its local same-thread worker fallback; no `blob:` worker allowance is added. Actual custom-scheme worker behavior, WASM decoder behavior and performance require native Ubuntu evidence.

## Bounds and cancellation

Inputs: 128 MiB per PDF, 10,000 extracted pages, 16 MiB UTF-8 text. Export: 32 MiB canonical snapshot, 64 MiB per image, 256 MiB combined images, 2,000 physical output pages and 256 MiB output PDF. Local resource assets are limited to 4,096 files / 128 MiB. Original attachments remain available through portable export; missing, oversized or unsupported image rendering retains the rich-print fallback/omission behavior.

The Windows native deadline is 110 seconds; the parent allows at most 2 minutes and a 2 GiB job-memory limit. Its WebView child tree is assigned to one job before the input gate opens. Before profile deletion, the parent requires the Windows job to report zero active processes; otherwise it retains private files and returns an explicit cleanup error. These Windows interfaces still require target execution.

The previous Linux process-group monitor did not enforce a whole-process domain. Exact WebKitGTK 2.52.6 source does not pass `--new-session` to bubblewrap, but its seccomp rules do not prohibit session/group changes, and an alternate Flatpak launcher can create externally parented browser processes. A process-group RSS sum or empty-group observation therefore cannot establish the required aggregate-memory/cleanup boundary. Linux now refuses capability lookup, private job staging and execution before reading a PDF or creating a WebView profile; an installed helper cannot override the refusal. Production Linux bundles omit the helper and `document_pdf` capability, and packaging rejects older bundles that advertise or contain it. Original source files remain retained.

The Unix diagnostic monitor also now limits `ps` to 250 ms plus a 100 ms bounded pipe wait and 4 MiB output. It requires the actual group leader, rejects malformed/duplicate identities and negative memory, and checks multiplication/addition overflow. This strengthens diagnostic failure handling; it does not turn process groups into a browser containment boundary.

## Reproducible target build and packaging

On the selected native host, run `scripts/build-native-portable.py --target windows-amd64|linux-amd64 --cache <verified cache> --output <new directory>`. The Windows PDF stage verifies the pinned Node/locked frontend tools, builds the PDF.js/print assets offline, uses the pinned official Windows SDK, and records native commands, dependency identities, hashes and notices. Windows requires the official reviewed SDK archive in the cache. Linux skips the PDF stage, and directly invoking the standalone Linux document builder returns the containment-unavailable error before compilation. The build does not acquire tools or dependencies. `--plan` is read-only and explicitly unqualified.

The desktop packager now rejects incomplete, fixture-only, changed or foreign-target OCR/PDF artifacts. OCR includes the exact Tesseract/Leptonica runtime and English-model identity. Windows PDF validation binds every asset byte and its minimum runtime. Linux packaging rejects document helpers and PDF capabilities. The retained Linux source-manifest validator still checks policy-extension hashes for future development; that does not enable packaging or execution. Capability claims without their required files fail packaging. Existing model-free operation remains independent of AI model packs.

## Evidence and remaining release checks

[Recorded local evidence](../../evidence/completion/portable-documents/manifest.json) separates host tests from native target execution. Independent browser fixtures use manually generated valid PDF xrefs, exact page text, physical page counts, hostile OpenAction/URI entries, malformed PDFs and an over-limit catalogue. Go tests cover retained input, mode isolation, changed assets, bounds, permission metadata, active cancellation, and uncertain-exit profile retention. Package tests reject changed models, helpers, policy extensions and resources. Windows/Linux Go compilation is source evidence only.

**No Windows or Ubuntu C++ helper build, WebView launch, rendered-PDF visual inspection, device execution, installation, signing or target performance has been established on this Mac.** The local browser fixture is Chromium, not WebView2 or WebKitGTK. Clean native machines must exercise the exact pinned build, all-request offline interception (including workers), output pages/images/fonts, encrypted/malformed/scanned PDFs, live cancellation/profile cleanup, package installation, offline operation, and the full applicable release matrix. This package does not close REL-009 or the native PDF release gate. The [containment correction evidence](../../evidence/completion/document-containment/manifest.json) supersedes the earlier Linux availability and whole-tree monitoring claims; historical test logs remain unchanged. System audio and screenshot acquisition remain separate gaps.
