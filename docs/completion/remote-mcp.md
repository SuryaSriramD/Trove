# Optional remote MCP: implementation and qualification

EXT-004 now has an opt-in HTTPS transport in the owning desktop process. It forwards through the existing `ProviderBridge`, canonical kernel, grants, proposal review, idempotency and disconnect paths. It never opens a second workspace or database. Actual reachable hosted-client qualification remains open; the evidence below uses synthetic clients, certificates and loopback sockets.

## Owner workflow

1. Open Remote MCP access in the provider panel. It starts disabled after every application launch or workspace change.
2. Enter the public HTTPS origin, explicit listener IP/port, and any exact HTTPS browser origins that need CORS. Select a certificate chain and matching unencrypted PEM private key through native dialogs. The certificate must currently cover the public hostname. Its private key and file paths never enter the renderer, workspace file selection registry, workspace content, model context or provider token responses. Selection returns a single-use, ten-minute in-memory handle.
3. Enable the listener explicitly. DNS/routing/firewall reachability and a certificate trusted by the intended client must already be arranged by the owner; Trove does not provision public hosting, install a tunnel, or expose a second headless kernel.
4. Select pages and tools, review the selected context, then create an opaque connection URL. Enter that URL in the hosted client. The URL identifies a scoped resource; it is not a bearer credential.
5. Review the requesting client in native Trove. Compare the browser code, inspect the public client identifier/metadata address, exact return address, pages and tools, then approve or deny. Client-supplied names are labeled as such. Browser authorization endpoints cannot grant pages. One client identity is bound to each connection; another client needs a separately created connection.
6. Read calls follow the existing live grants. Writes enter the same proposal queue as local clients and require native approval. Disconnect or disable stops requests and revokes the underlying canonical grant. Native consent decisions persist a public client ID and review hash in `provider_audit`; tokens, authorization codes and browser state are not recorded.

## Protocol and credential boundary

- Pinned official `github.com/modelcontextprotocol/go-sdk v1.8.0` handles MCP protocol semantics and client interoperability. The remote seam applies exact TLS Host and approved Origin checks before selecting separate SDK transports. The existing local handler retains its original no-browser-Origin and SDK loopback protections. Both legacy 2025-11-25 sessions and current 2026-07-28 stateless calls are exercised.
- RFC 9728 protected-resource metadata is published at the resource-specific well-known URL; RFC 8414 authorization-server discovery advertises only supported methods. OAuth authorization-code flow requires S256 PKCE, exact registered redirects, resource indicators on authorization and code-exchange requests, and returns the advertised RFC 9207 `iss` on successful and denied redirects.
- Preferred CIMD registration accepts a public HTTPS client metadata document whose `client_id` exactly matches its URL. Dynamic registration is also available for compatibility. This bounded implementation supports **public clients with token endpoint method `none`**. It does not advertise `private_key_jwt`, client secrets, upstream token passthrough, or client-credentials grants. During the current CIMD metadata transition, a published plural method list must include `none`; a legacy singular method must be absent or `none`.
- CIMD fetching uses HTTPS port 443, normal certificate verification, no proxy, no redirects, an eight-second timeout and a 64 KiB JSON limit. Every DNS result must be public; the verified result is pinned for the actual connection. Private/link-local/loopback/documentation/translation ranges are rejected. No logo, client URI or JWKS URL is fetched.
- Refresh compatibility is narrowly scoped: if a refresh request omits `resource`, the server can recover only the exact client/resource already bound to that unexpired refresh token. An explicit different or empty resource is rejected. Initial authorization and code exchange always require the resource. This accommodates the pinned Go SDK's default `oauth2.TokenSource`, whose refresh request omits the indicator, while retaining the original audience. The SDK automatic-refresh path is exercised by expiring its initial token in the fixture; it is not patched or simulated. [RFC 8707 section 2.2](https://www.rfc-editor.org/rfc/rfc8707.html#section-2.2) leaves accepted refresh resources to server policy; MCP clients should still send the parameter required by the current MCP specification.
- Browser review uses a random Secure/HttpOnly/SameSite=Lax cookie scoped to one review URL, a five-minute pending request, escaped static HTML, no third-party assets, no-referrer policy and frame denial. An owner decision requires the immutable review hash. The code is one-use and valid for one minute.
- Access tokens are opaque, resource/client-bound, held as hashes in memory, and expire after ten minutes. Refresh tokens are issued only when the client's declared grants include `refresh_token`; they rotate, have an eight-hour absolute family lifetime, and retain bounded spent-token hashes for replay detection. Code replay or refresh replay revokes the connection. Revocation invalidates the canonical grant and SDK sessions. Disable/restart clears all OAuth registrations, consent attempts and credentials; reconnect requires fresh native consent.
- The public boundary accepts standard `Authorization: Bearer`, without requiring a custom Trove connection header. Only after OAuth verification does the in-process wrapper substitute the separate private bridge credential and connection ID. OAuth credentials never reach model tools or another upstream provider.

## Bounds and recovery

There are at most 32 remote connection records per enabled listener, 32 pending authorization records, 128 dynamic registrations, eight token families per connection and 128 refresh rotations per family. Accepted TCP connections are capped at 128 and HTTP concurrency at 64, aggregate requests at 20/second with burst 80, and registration/CIMD fetches at one per six seconds with burst ten. Bodies are capped at 1 MiB (MCP) and 64 KiB (OAuth forms/registration); request headers are capped at 16 KiB. Header/read/write/idle deadlines are 5/30/45/30 seconds. Existing SDK sessions are capped at 32 per connection with a five-minute idle expiry, and tool calls at 32 per connection.

Invalid hosts, unapproved browser origins, plaintext requests, expired certificates, stale grants, token reuse, wrong resources, duplicate security parameters, wrong redirects and invalid PKCE fail closed. A failed listener closes its connections; the owner selects a certificate and explicitly enables it again. Expired pending consent is removed and must be restarted by the client. Limits or registration expiry require a fresh flow; a listener reset clears accumulated connection records. No connection automatically reconnects or widens its scope after restart.

## Local evidence and remaining gate

- `internal/providers/remote/server_test.go`: real TLS official SDK clients for CIMD and DCR discovery, authorization, native consent, tool calls, automatic SDK refresh, refresh rotation/replay, explicit revocation; code replay, wrong PKCE, resource isolation, exact redirects, expired/denied consent and issuer response, review cookies, Host/Origin/TLS policy, redacted status and bounded connection records. The CIMD source-fetch seam is synthetic; public-address and metadata URL policy are independently exercised.
- `internal/workspace/provider_remote_test.go`: real TLS plus actual SQLite kernel and existing bridge for both protocol versions; selected page succeeds, private sibling fails, proposed child stays absent until the shared approval service commits it, retry creates exactly one child, consent reaches canonical audit, and disconnect stops tool discovery.
- `app_provider_remote_test.go`: unexpected native file paths/fields, wrong workspace, external/local-AI actors and revoked owner grants cannot access native remote control.
- `frontend/tests/remote-mcp.browser.spec.ts`: actual Chrome with synthetic native IPC verifies disabled default, opaque certificate handles, selected-page review, client/redirect/comparison-code consent, and disabling all access.

These checks do **not** qualify public DNS/NAT/firewall reachability, a real hosted ChatGPT/Claude account, organization policy, production certificate installation/renewal, or the final packaged macOS workflow. EXT-004's real-client connectivity acceptance and the related EXT-005/C5 live gate stay open until those authorized environments are available. No public listener, live sign-in or existing user credential was used during implementation.

## Primary interface evidence

Checked against the current published protocol and vendor documentation during implementation:

- [MCP authorization, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization): resource discovery, PKCE, resource indicators and token handling.
- [MCP client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration): CIMD preference and dynamic registration compatibility.
- [MCP authorization security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations): refresh rotation, HTTPS/redirect policy and SSRF boundary.
- [Official Go SDK v1.8.0](https://github.com/modelcontextprotocol/go-sdk/tree/v1.8.0): pinned transport and OAuth client/server middleware APIs.
- [OpenAI hosted connector authentication](https://developers.openai.com/plugins/build/auth): CIMD public-client `none`, plural/singular metadata transition, exact callbacks and issuer response. No callback domain is hardcoded; each client's validated metadata supplies its exact redirect set.
- [OpenAI MCP guide](https://developers.openai.com/api/docs/mcp) and [Claude MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector): remote HTTPS/authentication requirements. Their presence in documentation does not constitute live interoperability qualification.
